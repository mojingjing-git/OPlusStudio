# O+ Studio Rust 迁移计划

交付记录（2026-11-17）：0.5.0 已实现并打包，默认启动入口已切换；0.4.0 独立保留。14 项 Rust 测试、原生五项可逆实机写入、多分片宏、最终发布包保存/撤销、识别期间关闭后的恢复均通过。UI 检查包含 100%/150% 字号、窄窗口和 WebView2 高密度参数模拟。实测证据与尚未覆盖的实体多显示器 DPI 切换边界见 `docs/native-validation.md`。下文保留实施前的审查计划和原始验收要求。

状态：MiniMax Flash 独立复核通过，可开始核心实现。日期：2026-11-17。结论见 `docs/rust-migration-review.md`，响应见 `reports/rust-plan-review-final.json`。审查通过不替代后续实机验收。

## 目标与范围

交付可运行的 Windows Rust + Tauri 2 版本（0.5.0），第一阶段板载配置由 Rust 原生执行，正常使用不依赖 Python、Qt 或启动本地 HTTP 服务。沿用目前背键工作台的交互思路，保留 0.4.0 作为对照与回退。独立键鼠上报仍属第二阶段，不在本轮冒充已完成。

必须保留：设备发现及身份查询、六宏槽读取、单键与组合保持、定时宏及原触发标志、草稿与冲突检查、批量事务/备份/读回/失败恢复、精确撤销、型号预设和个人校正、配置导入导出、四马达/标准改键/RGB 已验证字段、XInput 实时测试。手动六键校正也应原生迁移，保留取消/断连后恢复。只读曲线可用详情显示；旧电脑映射与额外诊断保留经典工具入口，明确其为可选旧版功能。

## 技术与目录

```
native/
  Cargo.toml                   # workspace
  crates/oplus-core/           # codec、身份/能力、设置模型、校验、事务、导入导出
  crates/oplus-device/         # Windows BLE + XInput，命令行实机验收入口
  app/                        # Tauri 2 commands、操作状态与退出控制
  ui/                         # TypeScript + React + Vite，编译后嵌入本地资源
  fixtures/                   # 从现有代码及已记录实机数据生成的测试向量
```

- 后端以 Tokio 异步运行，`btleplug` 提供 Windows BLE；如实机通知/发现存在兼容问题，使用微软 `windows` 绑定替换此层，不改核心协议 API。
- 一个设备操作队列拥有 BLE 会话；配置操作串行，前端不能直接提交任意 opcode/任意 BLE 写入。
- Tauri command 参数与返回值使用 serde 类型；仅暴露发现、读取、验证后保存、撤销、导入导出等明确命令。CSP 禁止远程页面与脚本，不开放通用 shell/任意文件系统权限。
- UI 使用弹性网格、可访问的真实控件及本地系统字体，保留浅深主题、固定保存栏和窄屏布局。Windows 依赖 WebView2；交付时检查本机是否具备，不能把依赖缺失当作“可运行”。
- 新代码遵守 GPL-3.0-or-later，保留 x20ctl 来源与协议版权说明；Cargo.lock、前端 lockfile 和发布清单记录依赖。

## 迁移步骤与门槛

### A. 冻结行为与协议向量

在实现前记录基线、数据模型和错误语义。协议帧/CRC/XOR、特殊长度字段、serial、长记录分片、压缩键表、能力位、宏位布局与中立摇杆 nibble，均用 Python 当前实现导出黄金向量。Rust 编码必须逐字节相同；解析拒绝截断、长度错误与 CRC 错误。

不把整个 vendor 文件机械移植；只迁当前需要的配置能力，按模块保留来源。黄金数据不可包含新的猜测写命令。

### B. Rust 纯核心与事务

先用模拟 transport 跑单元测试和差分测试，再接 BLE。严格匹配 `1005:2001 / 1.37 / mode 6 / generation 2`；额外检查能力、按键列表和记录长度。禁止固件升级、摇杆/传感器工厂校准命令、恢复出厂、空槽清空以及未知字段写入。用户主动发起的“六键名称校正”仅通过已验证宏槽临时标记来识别名称，不是硬件工厂校准，属于允许并必须迁移的功能。

批量保存：读取新状态 → 校验全部草稿及 expected 原字节 → 备份成功落盘 → 逐槽写入并读回 → 返回精确撤销记录。将“准备尝试的槽”先记入恢复集合，部分写入失败也会尝试恢复该槽；反向恢复处理所有已尝试槽，某槽恢复失败不阻止其余恢复。错误包含备份位置及未确认的槽。即使界面断开或窗口要求退出，也不能直接丢弃正在恢复的任务。

数据文件保持兼容 `oplus-rear-v1` 和现有全板自动备份。导入先做大小、型号、布局、六槽唯一性和所有记录校验，只产生草稿；任何导入失败都不部分更新草稿。个人名称仍按地址保存，已验证型号预设可跨地址复用，不将 MAC 前缀当作型号证据。

### C. 实机只读验证

读取发现、身份、能力与六槽，同 Python 当前快照逐字节比对。通知处理按 opcode/serial/分片完整性校验，有超时、断连和重连清理；选择多个候选时要求明确选择，不自动猜目标。扫描本身不能触发设置写入。

Rust 进程内禁止并发 BLE 配置；采用跨进程文件锁避免两个新版本竞争。旧发布版不具备该锁，实机测试前关闭旧工具，发布版应拒绝与已知旧配置实例并行操作或提供等效保护。锁文件保存在本地应用数据目录，进程退出/崩溃后由 OS 释放句柄，不用遗留 pid 文件永久阻塞。

### D. UI 与应用生命周期

原生后端接通后再切换 UI。所有新 UI 后端调用必须走 Rust，不用 Python sidecar 冒充迁移。主界面显式区分游戏连接和配置读取状态、当前值和草稿、正在保存和已核对。失败保留草稿但使写入失效，重新读取后检查冲突。切换设备清除旧撤销记录。

后台写入任务由 Rust 持有，浏览器组件卸载/前端 Promise 被取消不停止事务。退出操作等待当前配置事务结束；校正取消应请求恢复后退出，不中断恢复。输入测试不启用键鼠注入。

### E. 真实写入、发布与默认切换

仅在 A–D 通过后做可恢复的单槽实验：读取/备份 → M1 临时设为 A → 读回 → 精确撤销 → 再次读取六槽，与原始基线一致。随后验证组合键和定时宏的编码/记录；读回不被宣称为物理时序测量。校正沿用已验证协议，只在有必要且用户就绪时安排实体键验证，已有名称不必重复识别。

只有编译成功、关键核心与集成测试通过、发布版启动及真实读取/保存/撤销通过、原配置恢复确认后，才更新 `Start-OPlus.cmd` 优先启动 Rust 版本。0.4.0 与源码不覆盖；产物放 `releases/0.5.0`，清单包含哈希、依赖版本、验收结果和已知限制。

## 验收清单

1. 黄金向量逐字节一致，错误帧/错误布局被拒绝；核心代码可不连接硬件测试。
2. 新鲜度冲突、空槽保护、部分写失败、读回不一致、恢复失败仍继续、取消/退出等路径有模拟 transport 测试。
3. Rust 原生完成实机身份和六槽读取；临时单槽写入及撤销后六槽与基线一致。
4. 导入错误不改草稿，个人名称优先，切换设备不复用旧撤销；保留备份兼容。
5. 发布版 GUI 可启动；100%/150%/200% 缩放和窄窗口下关键操作不被裁切，有清楚的错误、忙碌与保存反馈。
6. 用实测报告说明包体积和依赖；不预先承诺性能或内存数字，不把模拟缩放称为多物理显示器实测。

## 功能覆盖与故障边界补充

| 必须功能 | 实现阶段 | 必须验证 |
|---|---|---|
| 六槽保持/组合/定时宏/原 trigger | B、D、E | Python 黄金向量、导入导出往返、真机保存/撤销后六槽一致 |
| 四马达强度 | B、D、E | 保留尾部未知字节；原生最小单值修改、读回、恢复 |
| 标准按键映射 | B、D、E | 按设备键表排序；全零/空表规范化；RS 临时映射 LS 后恢复 |
| RGB 已验证颜色字段 | B、D、E | 只改支持灯区的三个 RGB 字节，保留模式/速度字段；最小颜色修改后恢复 |
| XInput 实时输入 | C、D | 未连接/连接/断连状态及轴范围、扳机和标准按键；只读，不注入输入 |
| 型号预设/个人名称 | B、D | 相同指纹跨地址复用，个人名称优先，重复名称/未知型号拒绝预设 |
| 六键引导校正 | B、D | 模拟全部完成、设置标记中取消、采样中断连、窗口关闭；所有尝试槽均恢复；实机实体按键验收仅在必要且用户就绪时进行 |
| 只读曲线与旧高级工具 | C、D | Rust 显示原始已读参数；经典工具可选入口，缺少旧产物时明确说明，不把它算作 Rust 原生功能 |

正常失败恢复覆盖可处理的传输错误、读回不一致、取消与有序退出。强杀进程、系统崩溃或断电不能承诺自动完成设备恢复：完整原始备份须在首个写入前完成原子落盘与文件同步，并记录未完成操作的恢复说明，下一次启动提示恢复入口，不能声称配置已自动恢复。该边界必须在发布说明中明确。

精确撤销记录由后端保存，包含设备地址/指纹、原始记录、成功写入后的 expected 字节及受影响槽；撤销重新读取，任一目标不匹配则不写任何槽。重启不恢复内存撤销历史，但可从备份导入恢复；切换设备清空旧撤销。

协议契约在 A 阶段明确冻结：当前设备响应 opcode 为 `0x19`，按当前单个在途请求的 serial 配对，不错误地要求响应 opcode 等于请求 opcode；`0x1F` 实时事件不能满足配置请求。长记录第一包带 declared，后续页只拼接原始数据，超长/空片段/超时拒绝；opcode、序号、长度和 CRC 的模拟通知用例覆盖不匹配及迟到响应。超时后的会话是否可用于恢复须显式定义，必要时重新连接并再次验证身份，不携带旧 pending 请求进入新会话。

旧发布版并发保护采用“尽力检测后拒绝配置”策略：在连接及配置操作前检查其他已知 O+ Studio 配置进程（不终止用户进程），存在旧配置实例则提示先关闭；新版本之间还必须获取同一个 OS 自动释放的独占文件锁。旧版不配合锁，检查后再启动旧版仍存在竞态，因此不承诺对旧二进制的绝对互斥；使用新版配置时应保持旧工具关闭。不能仅依赖旧程序并未使用的文件锁。

## 持久化事务日志契约（初审修订）

日志 schema v1 至少包含：操作 ID、设备地址与完整指纹、已同步备份的应用内相对路径与 SHA-256、受影响槽、每槽 original/target 字节、每槽状态及整个操作状态。日志和备份均位于应用数据目录；先写同目录唯一临时文件、同步文件，再原子替换。Windows 使用带持久化语义的替换操作；日志路径校验为应用目录内，禁止由 JSON 指向任意外部文件。

这里的“槽”泛指受影响配置记录，标识为 `rear_0..rear_5`、`motors`、`remapping` 或 `lighting`。普通保存、四马达/改键/灯光保存和精确撤销均复用同一个事务引擎、备份与日志协议，不另设无日志写入路径。

顺序必须为：

1. fresh snapshot 与全量校验 → 完整备份原子写入并同步 → 创建 `prepared` 日志并同步。任一步失败不得写设备。
2. 每个槽先将不可回退的 `attempted=true` 及状态 `write_intent` 同步，再发首个写片段；设备写入及读回一致后状态改为 `verified` 并同步，但 `attempted` 始终保持 true。失败发生在意图落盘后、首个设备包前时，该槽也属于“可能已写入”，不能假定未写。
3. 所有目标槽核对后，将整个日志改为 `completed` 并同步，之后才能向界面报告保存成功、生成撤销记录。提交日志失败进入恢复路径，不能假报成功。
4. 任一写入/核对/日志提交失败，按相反顺序尝试恢复所有 `attempted=true` 且尚未 `restored` 的槽，**包括当前状态为 verified 的先前成功槽**。每槽尽可能先同步 `restore_intent`；恢复读回后同步 `restored`。恢复阶段日志写入失败不能阻止其他槽的设备恢复；既有未完成日志仍保留为不确定状态，错误同时说明设备恢复与日志状态。
5. 恢复全部确认且日志同步后标记 `rolled_back`；存在未确认槽时保留 `recovery_required`，若磁盘故障使其不能落盘，旧的非终态日志也必须在启动时被识别为未完成。

启动只枚举应用日志目录的有限大小 JSON，查找非 `completed` / `rolled_back` 的记录。先验证日志结构、备份路径/哈希、型号与记录格式；显示未完成操作及可能受影响槽，**不自动写回手柄**。恢复操作由用户选择，重新连接核实设备、读取当前值并预览差异，再以新事务执行所选原始记录；当前值已等于原始值的槽跳过。无法读取或身份不匹配时只提供备份位置，不尝试写入。

跨重启的可能受影响集合仍为日志中 `attempted=true && state!=restored`，不会因为 verified 被漏掉；明确未尝试的 planned 记录不列入集合。精确撤销是新的 `kind=undo` 事务，原始字节取“撤销前当前值”，目标取上次保存前记录；撤销中失败时回滚所有尝试记录到撤销开始前状态，崩溃则保留同样的日志并走同一启动恢复入口。只有撤销完成并同步终态后才消费内存撤销记录。

六键名称校正使用 `kind=identification` 的同一日志机制；临时标记写入并核对后进入非终态 `sampling`，不能当作 completed。采样结束、取消或断连后恢复全部 attempted 记录，确认并同步后标为 rolled_back；仅在六个实体键均识别且原配置恢复确认后保存新的个人名称。采样中进程崩溃时，非终态日志将提示恢复临时标记。

崩溃模拟覆盖：备份同步前、prepared 后、write_intent 后但设备包前、部分片段后、读回后但 verified 前、提交日志失败、恢复读回后但 restored 前。重启检查必须区分确定未尝试槽与可能写入槽，不漏报；用户未选择恢复前必须零设备写入。

BLE 技术验证门槛：所选后端必须通过发现并识别候选目标；单目标环境完整身份及六槽读取、多目标环境明确选择及错误目标拒绝、订阅通知与全部支持表分片读取，以及错 serial/CRC/空片段/超时/断连清理测试。`btleplug` 不满足其中任一关键真实读取条件且无法修复时，切换 `windows` 绑定；这不阻止纯核心与模拟事务实现，但禁止跳过条件进入真实写入。

退出是可控有界操作：普通 GATT 请求 3 秒、连接 12 秒，校正采样最多 60 秒；单槽正常写入/核对有独立上限，返回错误后进入恢复。每槽恢复有独立截止时间并最多重连一次，总恢复预算不超过 180 秒，所有已尝试槽均须得到恢复尝试或明确的未确认记录。超时不通过粗暴取消整个事务 future 解决；由操作协调器完成日志收尾，保留恢复入口后允许退出。强杀/断电由上述启动恢复流程处理，不能保证设备自动还原。

## 独立审查要求

审查员阅读本计划与现有 `oplus/protocol.py`、`ble.py`、`board.py`、`rear.py`、`rear_identify.py` 及测试，重点检查功能遗漏、BLE 通知配对/分片、事务恢复、并发与退出、数据兼容、范围和验收是否足够。按“阻塞 / 重要 / 建议”列出问题，不操作真实手柄、不改设备状态。

发现阻塞项时先修改计划并回审；审查无阻塞后开始核心实现，不再为已授权的常规实现步骤重复询问。

## 复核重要项处理

- Windows 原子替换明确使用同目录临时文件写入并 `sync_all`，关闭写句柄后 `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`；失败保留旧文件并清理临时文件。不同文件系统/磁盘断电缓存的保证不超出 Windows 及存储设备契约，启动时必须对损坏日志/备份安全拒绝，不能据此承诺任意断电后的绝对持久化。
- 启动恢复重新读取并核验完整指纹及目标记录；当前字节等于原始值则跳过，等于目标值时才可按预览创建受 expected 字节保护的新恢复事务。若两者都不匹配，默认拒绝自动恢复覆盖并提供备份检查入口；用户可通过普通导入备份为草稿、逐项确认后保存，仍须经过 fresh snapshot 冲突检查，不提供未校验的强制写接口。
- 审查方式：独立 MiniMax-M3.1-Flash 模型读取计划全文，初审修订后复核，最终明确“可开始”。默认 Agent 调度未返回有效结果；改用用户授权的 MiniMax 模型，经本地 mmx SDK 指定官方 low effort 参数取得完整结论，未把空响应或思考截断算作审查通过。
