# 致动 O+ 适配记录

日期：2026-11-16（Asia/Shanghai）。用户确认是旧款致动 O+。最初通过 2.4G USB 接收器连接；随后拔掉接收器，改用 USB 数据线直连，完成模式与按键对照测试。

用户在 KeyLinker 中读取并提供：VID `1005`、PID `2001`、固件 `1.37`。蓝牙恢复后，电脑通过 BLE 核实了这些字段，并确认 mode 6 / generation 2。这是配置协议身份，与游戏接口的兼容 USB 标识是不同层级。最初的用户报告见 `device-owner-report.json`，实机身份报告见 `reports/oplus-identity-first.json`。

## 本机已观察

- Windows 存在 `USB\VID_045E&PID_028E\1187A89`，版本 `REV_0110`，服务 `xusb22`，总线描述 `Controller`。
- 子接口包括 `USB\VID_045E&PID_028E&IG_00` 与一个 HID game controller。不能从 Microsoft 的 VID/PID 推断真实厂商。
- XInput 槽位 0 在线，其他三个槽位在初次采样时未连接。
- 初次 PnP 枚举没有发现 present 的 Bluetooth 类设备。这表示当时未发现已启用的蓝牙适配器，不等同于主板一定没有蓝牙硬件。
- 扩展检查发现 Intel AX200 Wi-Fi 6（`8086:2723`）和 present 的 Intel 蓝牙 USB 设备 `8087:0029`。蓝牙没有绑定设备类别和服务，PnPUtil 显示 `Stopped`。
- `C:\Windows\INF\setupapi.dev.log` 记录 2026-11-15 15:54 依次卸载 `oem126.inf`、`oem96.inf`、`oem6.inf`，最后为此蓝牙硬件安装 `NULL driver`。当次检查的蓝牙驱动库为空。日志足以支持“当前驱动缺失”，不能据此确定是谁执行了卸载。
- 设备栈中的 `hrdevmon` 是火绒过滤驱动，但它出现于栈中本身不能证明阻断原因；没有修改安全软件设置。
- 用户授权后，于 2026-11-16 02:01 完成 Intel 官方 AX200 蓝牙驱动 `24.10.0.4` 安装。文件 SHA-256 与官网一致，Intel Authenticode 签名有效，安装返回 0。安装后 `8087:0029` 正常绑定 `BTHUSB`，驱动为 `oem13.inf`，实际 BLE 扫描可发现周边设备，全程未重启。
- 系统另有 ViGEm 虚拟总线；不能把它当成手柄的厂商配置接口。
- 初次诊断时尚未采集到用户按背键的数据；后续的 DInput 对照结果见下文，不能把初次缺少数据当成背键不独立的证据。
- HID 描述读取结果为 Usage Page `0x0001`、Usage `0x0005`，输入报告 15 字节、输出报告 0 字节、Feature 报告 0 字节。这个暴露的 HID collection 没有可写报告，不能据此否定其他模式或 USB 私有控制传输的可能性。

详细的只读报告在 `reports/hardware-initial.json` 以及后续程序生成的报告中。报告保存在本地，不上传。

## 公开资料

[致动官方下载页](https://www.zd2015.com/APP2) 分别列出手机应用和 PC 测试版适用范围。PC 测试版的页面标注是终极传奇特定固件版本，不能据此认定老款 O+ 已被支持。旧 O+ 与 O+ 卓越也不能混作同一型号。

[x20ctl](https://github.com/AmjadAAYD/x20ctl) 是对 KeyLinker 的开源逆向实现，采用 GPL-3.0-or-later。它提供了可复用的通信研究基础，但不证明 KeyLinker 或手柄固件本身开源。[协议文档](https://github.com/AmjadAAYD/x20ctl/blob/fce9627ea47af1532ee37c52d087983aa89d2d39/docs/01-protocol.md) 记录的主要配置通道是 BLE GATT：

| 作用 | UUID |
| --- | --- |
| 配置服务 | d7f010e0-660d-46e9-96c3-19c4148bdab5 |
| 命令特征 | d7f010e1-660d-46e9-96c3-19c4148bdab5 |
| 响应通知 | d7f010e2-660d-46e9-96c3-19c4148bdab5 |

身份模块实现身份、名称及能力表查询，并检查帧长度、CRC、响应类型和序列号。板载模块在精确身份匹配后提供已实测记录的读写、备份和失败恢复；实测范围见下文。不向 OTA 服务发送数据，不根据其他品牌的能力表推断 O+ 的可写格式。

[KeyLinker 官方说明](https://smart-one.cn/keylinker) 描述了蓝牙配置及与游戏设备同时连接的能力。本机实际发现的名称为 `致动O+_XXXXXX`，且已验证其配置服务。扫描界面保留全部附近设备，不只过滤 X20 的名字或 MAC 前缀。有线模式切换以本机固件 1.37 的实际观察为准，不从其他 O+ 型号或手册版本外推。

[Microsoft XInput 文档](https://learn.microsoft.com/en-us/windows/win32/xinput/getting-started-with-xinput) 说明标准输入包括两摇杆、两扳机、十字键及标准按钮，以及即时震动输出；没有 O+ 专属背键字段。[SendInput 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) 说明了软件键鼠注入和权限限制。

## 尚待确认

1. 独立键鼠输入留待第二阶段。六个宏槽与实体背键的对应已在 2026-11-17 的引导识别中确认，见下文；此前的 M1 / M2 默认输出记录仍保留。
2. 配置写入后的实体灯效、马达强度及重新开机持久化。记录读回一致不等于这些物理行为已全部验证。
3. 摇杆 / 扳机参数与未知灯光字段的准确含义。当前保持只读或保留原始字段，不猜测写入。
4. 若继续调查 BLE 按键实时流，先确认进入命令和响应，再对照手机 KeyLinker 的已知操作；可参考 Android Bluetooth HCI snoop log，其可用性取决于手机系统。

独立背键需要有独立输入通道或可切换的固件模式。若固件只上报常规按键，电脑版工具不能从相同的游戏输入还原实体按键来源。

## 已完成的 O+ 实机写入验证

截至 2026-11-16 02:14，已完成下列“读取、备份、单项修改、读回核对、恢复”实验：

| 设置 | 修改实验 | 结果 |
| --- | --- | --- |
| 马达记录 | 首字节 `bf → be → bf`，其余 7 字节不动 | 修改与恢复均逐字节一致 |
| 标准改键 | RS 临时映射 LS，随后恢复无自定义映射 | 逻辑映射恢复；空表由固件保存为 16 个零目标 |
| RGB 记录 | 第一项红色分量 `ff → fe → ff`，其余 23 字节不动 | 修改与恢复均逐字节一致；未据此宣称实体灯效已改变 |
| 第六宏槽 | 保持原按键 mask，只将时长 `0 → 5 ms → 0` | 修改与恢复均逐字节一致 |

详细帧和结果在 `reports/oplus-motor-roundtrip.json`、`reports/oplus-settings-roundtrips.json`，完整备份在 `%LOCALAPPDATA%\OPlusStudio\backups`。

实际能力表 `03 03 0f 00 3f 01 0b 00 c0 00` 报告 6 个宏槽、4 路马达及灯光能力位 0/1/3。三个压缩键表与 KeyLinker 第二代格式一致；背键通过宏槽配置，不伪造六个改键 source 码。

最初的 `0x1D 02 DF AB` 状态探针出现过 `0x1F` 触发器 / 摇杆数据；旧版 Button Test 页面探针漏发了启动实时流的命令，只重复选择页面，因此其零帧结果不能作为背键能力证据。修正后的按键测试见下文。所有探针均限时进入 / 退出；退出后的能力表未变、XInput 正常。

用户切换 USB 数据线直连并拔掉接收器后，XInput 模式仍是 `045E:028E`，HID 输入 / 输出 / Feature 长度仍为 `15/0/0`，没有同 VID/PID 的额外 collection。

## 有线 DInput 与 M1 对照

用户同时长按正面 Start + Back 后，采样先观察到 XInput 按钮位 `0x30`，约 1.1 秒后原设备断开，约 2.45 秒后出现 `0079:181C`。这次切换已由设备变化确认，不依赖用户是否看到提示。记录见 `reports/mode-watch-live.json`。

DInput 的 HID 输入 / 输出 / Feature 长度为 `10/5/0`，按钮 usage 范围为 1–15，另声明 Consumer usage 547。未向 5 字节输出报告发送猜测命令。WinMM 实际读取到 15 按钮、4 轴、居中状态及中立 POV `65535`。

第一次 M1 限时窗口只读到中立值，缺少普通按键对照，因此不作硬件结论。第二次在用户准备好后，按“正面 A 三次 → 停两秒 → 背面 M1 三次”采样，得到：

| 阶段 | 实际记录 | 解释 |
| --- | --- | --- |
| 正面 A | 按钮位 `1`，POV 中立；窗口中捕获两次按下 / 松开 | 普通按键读取正常；开始采样时 A 已按住 |
| 背面 M1 | 三次 POV `18000 → 65535`，按钮位始终为 0 | 当前设置输出十字键下，未在该通道出现独立按钮 |

完整时间戳见 `reports/dinput-A-then-M1.json`。采样使用 `joyGetPosEx` 读取按钮和 POV，不读取原始 HID 全部字段或 Consumer usage 状态，不能外推所有模式和全部背键。但它已经表明，直接映射当前可见的 M1 输出会与十字键下共用触发条件。15 个声明按钮本身不足以证明独立背键存在。

测试结束后用户重复 Start + Back，电脑确认恢复 `045E:028E`、XInput 槽位 0 在线，见 `reports/hardware-after-mode-test.json`。此次测试没有修改板载映射或宏。

## BLE 按键测试修正与 M2 对照

源码探针已改为先发送 `0x1D 02 DF AB` 启动实时流，再发送 `0x1D 05 DF AB 00 06 05` 选择按键页。增加了 XInput 同步事件记录；进入命令放在 `try/finally` 内，页面选择失败也会尝试停止并断开。两个回归测试覆盖准备完成后才启动、启动顺序和失败清理。

修正后的中立复测收到 8 个 `0x1F` 帧，见 `reports/oplus-live-button-start-fixed.json`。随后第一次 A / M1 窗口只捕到一组同步按压，不能可靠分配实体键名，故不用于推断 M1 的 BLE 输出。

为避免建立蓝牙连接挤占采样时间，最终改为连接并核实身份后等待操作者启动，实时模式本身仍最多 15 秒。用户事后确认这一轮实际按的是 **A 三次、M2 三次**，且仅最后一轮按了 M2；报告已更正为 `reports/oplus-live-armed-A-M2.json`。

| 实体按键 | XInput | 同步 BLE 数字事件 |
| --- | --- | --- |
| 正面 A | `0x1000`，标准 A | `02 01 01` / `02 00 01`，键码 1 按下 / 松开 |
| 背面 M2 | 三次 `0x2000`，标准 B | 三次 `02 01 02` / `02 00 02`，键码 2 按下 / 松开 |

本次没有观察到 M2 专属键码；不能把逻辑 B 直接命名成独立 M2 输入。此结果不用于改写前面的 DInput M1 标签，也不外推其他背键。BLE 已退出测试模式，退出后没有继续收到实时帧，能力表一致且 XInput 在线。此次测试没有修改板载配置。

## 2026-11-17：同类项目与识别策略复核

再次直接检索 GitHub 并阅读项目 README、协议文档及相关源码，确认不止一个 KeyLinker 桌面配置项目：

- [x20ctl](https://github.com/AmjadAAYD/x20ctl)：现有协议实现的参考来源，提供 [协议文档](https://github.com/AmjadAAYD/x20ctl/blob/main/docs/01-protocol.md)、能力查询及宏槽读写。当前产品以 EasySMX 型号为主，不能据此宣称已支持旧 O+。
- [PadTune](https://github.com/FrenchCaptn/PadTune)：Windows 配置器，动态查询按键表、宏按键表及可用宏槽；README 明确只有 NYXI Flexi 经过测试。`padtune.py` 的宏选择显示为 Macro 1、Macro 2 等通用槽名，未自动得出 O+ 的实体键丝印。
- [PadStudio](https://github.com/rauldev-yoru/padstudio)：Electron / React 与 Python BLE 后端组成的配置工作台，复用 x20ctl；`engine/backends/keylinker.py` 有宏读取、写入及读回接口，界面按槽编辑，不构成旧 O+ 实机兼容证明。
- [x20cfg](https://github.com/daMarxrider/x20cfg)：Linux EasySMX X20 工具，README 明确提供 BACK1/BACK2 配置命令及逆向笔记。

[KeyLinker 官方说明](https://www.smart-one.cn/keylinker) 将其描述为用于支持 KEYLINKER 协议的手柄的配置中心。共用协议与大量跨品牌设备的方向有依据，但目前没有可靠设备总数。

需要区分三件事：协议查询出宏槽及按键能力、宏槽与特定外壳实体键名称的对应、游戏接口是否上报独立背键。协议能力可直接查询；已知同型号与固件的实体对应可以用已验证的型号预设复用，不必每只从头按键。0.3.1 仍按蓝牙地址存名称且对未知设备要求识别，这是当前实现策略，不是 KeyLinker 的强制要求。尚未实现跨地址的型号预设复用；未知型号仍需核验对应关系。

## 2026-11-17：0.3.2 型号预设复用

借鉴通用 KeyLinker 配置器的能力查询方式，将已验证的外壳标签独立为型号数据。O+ 1.37 的身份、宏按键表和六槽位掩码同时匹配后，跨蓝牙地址复用 M1/M2/LM/RM/LK/RK；本机校正优先，避免重复名称。不按蓝牙地址前缀猜型号；未知固件或能力不套用。自动命名不建立连接、不写入配置、不启动临时标记；手动校正仍可用。此版本没有增加其他型号的写入许可。

93 项测试通过，新增跨地址复用、无硬件操作、未知固件/布局/能力拒绝预设、个人校正优先及新版界面自动显示名称的覆盖。协议代码来源继续在 NOTICE.md 保留；实体标签来自本项目已完成的六键实测。
